## What you will learn

- Define a tool with a schema the model can choose from
- Run the tool and return the result back to the model
- Write the tool description so the model picks the right one
- Keep the model out of the loop for anything that matters

## Why it matters

Tool use is how a model stops being a text generator and starts being a component in a system. The hard part is not the mechanics — it is writing tool descriptions and keeping authority where it belongs.

## A worked example

```python
TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Current weather for a city. Use for temperature and conditions.",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "City name, e.g. 'Bengaluru'"},
                "units": {"type": "string", "enum": ["metric", "imperial"]},
            },
            "required": ["city"],
        },
    },
}]

# The model proposes; your code decides.
if call["function"]["name"] == "get_weather":
    result = get_weather(**json.loads(call["function"]["arguments"]))
```

The description is the API for the model. Vague descriptions produce wrong tool choices more often than any model weakness does.

<Callout type="interview" title="Interview corner">
**A model can call a `delete_user` tool. How do you make this safe?**

Never let the model be the authorisation boundary. The tool implementation must check the caller’s permissions itself, using a server-side identity, not anything the model supplied. Keep destructive tools out of the tool list when the task does not need them, require an explicit confirmation step outside the model, and log every invocation with its arguments.
</Callout>

## Quick recap

- Tool descriptions are prompts — write them for the model, not for humans.
- Validate arguments in the tool, not just in the model’s schema.
- The model proposes; your code decides and authorises.
