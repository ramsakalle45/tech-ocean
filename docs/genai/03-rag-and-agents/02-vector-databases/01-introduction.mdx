## Why it matters

Vector search is the retrieval half of RAG. But it is also the half people over-engineer: for a corpus of a few thousand documents, a brute-force search in your existing database is simpler and often faster.

## A worked example

```python
def search(vectors, query, docs, *, k=5, bucket=None):
    """Brute force is fine below ~100k vectors, and much easier to reason about."""
    scored = []
    for doc, vector in zip(docs, vectors):
        if bucket and doc.metadata.get("tenant") != bucket:
            continue
        scored.append((cosine(query, vector), doc))

    scored.sort(key=lambda pair: pair[0], reverse=True)
    return [(round(score, 4), doc.text[:120]) for score, doc in scored[:k]]
```

Measure before reaching for a dedicated vector database. A `pgvector` column with an index, or a brute-force scan, is often the right answer for a first version.

<Callout type="interview" title="Interview corner">
**When would you not use a vector database?**

When the corpus is small enough to scan, when your data is in a relational database and you need transactional consistency with it, or when your search is mostly exact-match or keyword rather than semantic. In those cases a `pgvector` extension or a plain table plus a full-text index is simpler to operate and often faster.
</Callout>

## Quick recap

- ANN trades a little recall for a lot of speed.
- Filter before you rank, or the filter has to be applied to every candidate.
- Do not add a vector database before you have measured the need.
