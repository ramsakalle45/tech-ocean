## What you will learn

- Build a small, representative evaluation set
- Choose a scoring method and know when it needs a human
- Run an eval in CI and gate a release on it
- Tell the difference between a regression and a legitimate change

## Why it matters

Without evals, every prompt change is a guess and every model upgrade is a gamble. With evals, change becomes a controlled experiment — and you can prove the improvement.

## A worked example

```python
JUDGE_PROMPT = """You are grading an answer against a reference.
Score 1-5 on correctness, then 1-5 on unsupported claims.
Return JSON: {"correctness": n, "grounded": n, "reason": "..."}"""

def score(case: Case, answer: str) -> Score:
    verdict = llm_json(
        JUDGE_PROMPT,
        question=case.question,
        reference=case.reference,
        answer=answer,
    )
    return Score(
        correctness=verdict["correctness"],
        grounded=verdict["grounded"],
    )

# A release gate: the new prompt must not regress the score.
if mean(scores) < BASELINE - 0.05:
    raise SystemExit("eval regression")
```

A judge model scores answers, but it should never see which variant produced them, and you should spot-check its verdicts against human judgement periodically.

<Callout type="interview" title="Interview corner">
**How do you build an evaluation set when you have no users yet?**

Write it by hand. Take a hundred questions a real expert would ask, with their expected answers, and include the awkward ones — ambiguous questions, questions with no answer in the corpus, and questions that look similar but are different. The set is small and curated on purpose; it does not need to be large, it needs to be representative and to keep growing.
</Callout>

## Quick recap

- A small, curated eval set beats a large generated one.
- Evaluate retrieval and generation separately.
- Gate releases on evals, not on optimism.
