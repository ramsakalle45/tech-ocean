## What you will learn

- Estimate the cost of a request from tokens and model rates
- Find the latency budget of a request and know which part is slow
- Apply the levers: smaller model, shorter context, caching, batching
- Set per-user and per-feature budgets that actually hold

## Why it matters

Cost and latency are the two constraints that determine whether a feature ships. Both are dominated by a small number of levers, and both get worse linearly if nobody watches them.

## A worked example

```python
def estimate_cost(prompt_tokens: int, output_tokens: int, rate_in: float, rate_out: float) -> float:
    """Rates are per million tokens."""
    return (prompt_tokens * rate_in + output_tokens * rate_out) / 1_000_000

# 2k in, 500 out
per_call = estimate_cost(2000, 500, rate_in=0.15, rate_out=0.60)
print(f"${per_call:.4f} per call, ${per_call * 10_000:.2f} per 10k calls")
```

Output tokens are usually priced higher and usually grow faster than you expect, because "be concise" in a prompt is a request, not a guarantee.

<Callout type="interview" title="Interview corner">
**Your feature costs 40% more than last month. Where do you look first?**

Compare the token mix, not the total. Did input tokens grow — often because a prompt template picked up extra context, or a feature started sending more documents? Did output tokens grow because the model became more verbose? Or did traffic grow? Each has a different fix: trim the prompt, cap output length and enforce a schema, or add caching and a smaller model tier.
</Callout>

## Quick recap

- Cost is dominated by tokens; output tokens are the expensive half.
- Time to first token is what a user perceives as responsiveness.
- Cache aggressively and set hard budgets per user.
