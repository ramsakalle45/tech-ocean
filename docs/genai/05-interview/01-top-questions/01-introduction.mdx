## What you will learn

- Explain the design choices behind a RAG system you built
- Answer questions about hallucination, cost and latency with specifics
- Discuss evaluation and guardrails at a level that sounds like experience

## Why it matters

These questions test judgement, not trivia. The interviewer wants to hear how you decided, not what you memorised.

## A worked example

```text
Interviewer: "Your RAG system sometimes answers with old pricing.
            How do you debug it?"

Good answer:
  "First I would separate retrieval from generation. If the
   current pricing document is not in the retrieved set, it is an
   indexing or chunking problem — probably the document is behind
   a version tag the filter excluded, or its chunk is too large
   and the embedding drifted. If it is in the set and the answer
   is still wrong, I would look at the ordering: the pricing
   document may have been retrieved but ranked below a more
   semantically similar document. That points at reranking and
   at recency, not at the prompt.

   I would add both to a regression eval set before changing
   anything."
```

The structure is: separate the stages, check the data, then the prompt. That is a habit, and interviewers are listening for it.

<Callout type="interview" title="Interview corner">
**How do you reduce hallucination?**

Give the model a way to refuse, and make it explicit that it should. Ground the answer in retrieved context and require citations, so a wrong claim is visible. Then constrain the output format when you can, since free-form prose has room to drift. Finally, measure it — a groundedness metric on a fixed eval set — so you can tell whether a change helped. None of these eliminates hallucination; they make it rarer and more visible.
</Callout>

## Quick recap

- Separate retrieval failures from generation failures.
- Answer with structure: decision, evidence, and what you would do next.
- Have a real number ready for quality, cost and latency.
