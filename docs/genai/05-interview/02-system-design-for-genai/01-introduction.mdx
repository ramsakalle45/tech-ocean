## What you will learn

- Design a chat assistant with retrieval, tools, memory and guardrails
- Plan the offline and online components of a GenAI system
- Reason about the data flow from ingestion to answer
- Identify the failure modes of each component and what to monitor

## Why it matters

A GenAI design interview is a system design interview with one extra, probabilistic component. The fundamentals still apply; the new part is retrieval, and the honest handling of uncertainty.

## A worked example

```text
OFFLINE (per document, on change)
  parse → chunk → embed → index → record version

ONLINE (per request)
  question
    → rewrite
    → retrieve (filtered, hybrid)
    → rerank → top-k
    → assemble prompt with citations
    → generate (streaming)
    → validate output
    → guardrails
    → respond, with sources

ALWAYS ON
  trace everything · sample for human review · run offline evals on change
```

Draw the two flows separately. Most GenAI design interviews go wrong because the ingestion path and the request path get mixed together on one diagram.

<Callout type="interview" title="Interview corner">
**How do you keep the index fresh when documents change?**

Give every document a version and a content hash. On change, delete the chunks for that document and re-index; on delete, remove them. For the online path, either filter on the current version or update in place. For a large corpus, do it incrementally and asynchronously, and track the lag — an index that is a week stale is a different product, and the team should know that number.
</Callout>

## Quick recap

- Draw ingestion and request paths separately.
- Version your documents and index them incrementally.
- Every component needs a monitor and a failure story.
