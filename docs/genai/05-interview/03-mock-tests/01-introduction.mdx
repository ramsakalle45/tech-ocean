## A worked example

```python
# Round One, Problem 2 — build the evaluation harness.
#
# "Given a corpus of documents and a set of questions with the
#  document that answers each one, write a function that measures
#  retrieval recall@k and reports the misses."

def evaluate_retrieval(corpus, questions, *, k=5) -> Report:
    misses = []
    hits = 0

    for case in questions:
        retrieved = vector_search(case.question, limit=k)
        ids = {chunk.document_id for chunk in retrieved}

        if case.answer_document_id in ids:
            hits += 1
        else:
            misses.append(Miss(
                question=case.question,
                expected=case.answer_document_id,
                got=sorted(ids),
            ))

    return Report(
        recall_at_k=hits / len(questions),
        misses=misses,
    )
```

The misses are the output that matters. They tell you which documents to inspect for chunking problems.

<Callout type="interview" title="Interview corner">
**Your assistant works in testing but fails in production. How do you debug?**

Compare the traces. The likely differences are data (production corpus is different or noisier), retrieval (a different query distribution, or a filter that excludes too much), and configuration (a different model tier, a prompt that depends on a variable that is set differently). Pull the failing request IDs, replay them against the evaluation set, and see whether the eval set is even representative — if it passes on your own questions and fails on real ones, your eval set is the problem.
</Callout>

## Quick recap

- State the design, then the trade-offs, then the metrics.
- Build the evaluation harness before the feature.
- Production failures are usually a distribution difference.
