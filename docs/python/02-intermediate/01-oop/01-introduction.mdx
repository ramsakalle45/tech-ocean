## What you will learn

- Model a domain with classes that hide their internals behind a small interface
- Use `__init__`, `__repr__`, `__eq__` and the other dunder methods purposefully
- Tell a dataclass from a plain class, and know when composition beats inheritance
- Write a class that is easy to substitute in a test

## Why it matters

Classes are not about reusing code — inheritance is often the wrong tool for that. They are about giving a set of data a name and a set of rules, so the rest of the program can depend on the name instead of the shape.

## A worked example

```python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class Money:
    amount: int      # minor units, to dodge float rounding
    currency: str = "GBP"

    def __post_init__(self) -> None:
        if self.currency not in {"GBP", "EUR", "USD"}:
            raise ValueError(f"unsupported currency: {self.currency}")
```

`frozen=True` makes it immutable and hashable; `slots=True` cuts the memory cost per instance. Both are good defaults for a value type.

<Callout type="interview" title="Interview corner">
**When would you choose composition over inheritance?**

Almost always, when the relationship is "has a" rather than "is a". Inheritance couples you to the base class permanently; composition lets you swap the part. Reserve inheritance for cases where you genuinely want substitutability — a type hierarchy you control, where every subclass really is a kind of the parent.
</Callout>

## Quick recap

- A class gives data a name and a set of rules.
- `__repr__` and `__eq__` are what make a class debuggable and testable.
- Prefer composition; use inheritance only for substitutability.
