## What you will learn

- Catch the right exception, at the right level, with the right amount of context
- Write a custom exception that carries useful information
- Use the `with` statement so files close even when the body raises
- Handle encoding, large files and partial writes without corrupting data

## Why it matters

Every long-running program eventually hits an error. Where you handle it decides whether a failure is a logged warning or an outage. Catching too broadly hides bugs; catching too narrowly crashes on inputs you did not predict.

## A worked example

```python
from pathlib import Path

def read_lines(path: Path) -> list[str]:
    try:
        with path.open(encoding="utf-8") as fh:
            return fh.read().splitlines()
    except FileNotFoundError as exc:
        raise FileNotFoundError(f"no such config: {path}") from exc
    except UnicodeDecodeError as exc:
        raise ValueError(f"{path} is not utf-8 text") from exc
```

`from exc` keeps the original traceback visible, so you can see both the cause and your explanation. Never use a bare `except:` — it swallows `KeyboardInterrupt` and `SystemExit` too.

<Callout type="interview" title="Interview corner">
**Where should you catch an exception?**

As close to the point of failure as you can add useful context, and no further. Catch it low if you can retry or fall back; let it travel if the caller is in a better position to decide. A top-level `except Exception` that only logs and continues is almost always hiding a bug.
</Callout>

## Quick recap

- Catch specific exceptions, never bare `except:`.
- Add context with `raise ... from exc` — it keeps the cause visible.
- Use `with` for anything with a lifecycle, especially files.
