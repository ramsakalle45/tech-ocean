## What you will learn

- Distinguish concurrency from parallelism, and I/O-bound from CPU-bound
- Use a thread pool for blocking I/O and a process pool for CPU work
- Write `async` code that does not block the event loop
- Explain what the GIL changes about each of these choices

## Why it matters

Concurrency is how a single-threaded program waits on many slow things at once. Choosing the wrong tool costs you either throughput or the whole event loop.

## A worked example

```python
import asyncio

async def fetch(session, url):
    async with session.get(url) as response:
        return await response.text()

async def main(urls):
    async with aiohttp.ClientSession() as session:
        return await asyncio.gather(
            *(fetch(session, url) for url in urls)
        )
```

`asyncio.gather` runs the coroutines concurrently on one thread. If any coroutine does blocking work — a sync HTTP call, `time.sleep` — it stalls every other task.

<Callout type="interview" title="Interview corner">
**Your program makes 100 HTTP requests and takes 30 seconds. Each request takes 300ms. What is the problem?**

The requests are I/O-bound and are being made sequentially. With a thread pool or `asyncio.gather` they should take roughly 300ms plus overhead, not 30 seconds. The first fix is concurrency; the second, if you still need it, is connection pooling and keep-alive.
</Callout>

## Quick recap

- I/O-bound: threads or asyncio. CPU-bound: processes.
- Never block the event loop — no `time.sleep`, no sync I/O inside `async def`.
- The GIL limits CPU-bound threads, not I/O-bound ones.
