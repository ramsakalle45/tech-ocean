## Why it matters

Python hides memory management, but it does not remove it. Understanding when objects are freed explains a whole class of surprising behaviour — dangling references, memory that grows and never shrinks, and threads that do not scale.

## A worked example

```python
import sys, weakref

class Node:
    pass

node = Node()
print(sys.getsizeof(node))            # 48 bytes plus the dict

ref = weakref.ref(node)
del node
print(ref())                          # None — collected immediately

# A cycle is different:
a, b = Node(), Node()
a.other, b.other = b, a
del a, b
# still alive: the cycle keeps both alive until the GC runs
```

Reference counting frees most objects the instant the last reference goes. Only cycles need the garbage collector.

<Callout type="interview" title="Interview corner">
**Does the GIL make Python single-threaded?**

It makes *CPU-bound* Python code effectively single-threaded, because only one thread executes bytecode at a time. It releases the lock during I/O, so I/O-bound threads scale well. It also does not protect CPU work written in C extensions that release the GIL, which is why NumPy scales across threads.
</Callout>

## Quick recap

- Reference counting frees objects immediately; cycles need the GC.
- The GIL limits CPU-bound Python threads, not I/O-bound ones.
- Measure before optimising: `tracemalloc` and `sys.getsizeof` answer most questions.
