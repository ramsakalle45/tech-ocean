## What you will learn

- Profile before you optimise, and read a profile output correctly
- Tell an algorithmic problem from an implementation detail
- Apply the optimisations that pay: local variables, comprehensions, `__slots__`
- Avoid the optimisations that cost more than they save

## Why it matters

Most "Python is slow" claims are about the algorithm, not the language. A profiler turns a vague feeling into a number, and a number tells you whether the work is worth doing.

## A worked example

```python
import cProfile, pstats, io

pr = cProfile.Profile()
pr.enable()
result = process_the_data(rows)
pr.disable()

s = io.StringIO()
pstats.Stats(pr, stream=s).sort_stats("cumulative").print_stats(12)
print(s.getvalue())
```

Sort by `cumulative` to find the call tree cost, and by `tottime` to find where the time is actually spent. The difference between those two is where most misreadings happen.

<Callout type="interview" title="Interview corner">
**A function gets slower as you add more items to a list it reads. What is a likely cause?**

A linear scan inside a loop — the classic O(n²). Check whether the inner body does a membership test against a list where a set or dict lookup would be O(1). Profiling would confirm it, but the shape of the slowdown points straight at it.
</Callout>

## Quick recap

- Profile first. Every time.
- Algorithmic wins beat micro-optimisation by orders of magnitude.
- Optimise for readability unless measurement says otherwise.
