## What you will learn

- Write tests that fail for the right reason and read clearly
- Use fixtures and parametrisation to avoid copy-paste
- Package a project with `pyproject.toml` so it installs cleanly anywhere
- Set up a virtual environment and dependency pinning that a colleague can reproduce

## Why it matters

Tests are how a codebase keeps its promises as it changes. Packaging is how anyone else can use it at all. Both are small investments that prevent expensive failures.

## A worked example

```python
import pytest

@pytest.mark.parametrize(
    ("total", "expected"),
    [(0, 0), (1, 1), (100, 4950)],
)
def test_sum_to_n(total, expected):
    assert sum(range(total + 1)) == expected


def test_rejects_negative():
    with pytest.raises(ValueError, match="non-negative"):
        sum_to_n(-1)
```

Parametrisation turns one test into many cases with no copy-paste. `pytest.raises(..., match=...)` asserts on the message too, so the error stays meaningful.

<Callout type="interview" title="Interview corner">
**What is a good rule of thumb for what to test?**

Test behaviour that matters to the people using the code, and the edges where it breaks: boundaries, empty inputs, error paths. Do not test the language or the framework. If a test would still pass if you rewrote the implementation, it is testing the implementation, not the behaviour.
</Callout>

## Quick recap

- A good test name reads like a specification.
- Parametrise instead of copy-pasting.
- Pin dependencies in a lockfile so a colleague gets the same tree.
