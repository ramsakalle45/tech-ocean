## What you will learn

- Choose the right join type for the question being asked
- Predict the row count of any join before running it
- Write an anti-join and a self-join without subquery gymnastics
- Spot a join that has accidentally multiplied your rows

## Why it matters

A join is a promise about which rows survive. Choosing the wrong one silently drops data or duplicates it, and the query still returns a plausible-looking number.

## A worked example

```sql
-- Anti-join: customers who have never ordered.
SELECT c.id, c.name
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- Self-join: every employee and their manager.
SELECT e.name AS employee, m.name AS manager
FROM employees AS e
LEFT JOIN employees AS m ON m.id = e.manager_id;
```

The `LEFT JOIN ... WHERE o.id IS NULL` pattern is the standard anti-join. It relies on `id` being non-null, which is true for a primary key.

<Callout type="interview" title="Interview corner">
**A query returns 10,000 rows from a join, but each table has 100 rows. What happened?**

Fan-out. The join produced 100 × 100 combinations, meaning the join key is not unique on at least one side, or the condition is too loose. Check the cardinality of the key on both sides before joining, and aggregate first if you only need summary rows.
</Callout>

## Quick recap

- Left join keeps unmatched left rows; inner join keeps only matches.
- Count the rows before and after the join when a total looks wrong.
- Anti-joins are `LEFT JOIN` plus `IS NULL`.
