## What you will learn

- Use a scalar subquery, a correlated subquery and an `EXISTS` for the right situation
- Break a hard query into readable CTEs
- Write a recursive CTE for a hierarchy
- Avoid the correlated subquery that runs once per row

## Why it matters

Nested queries are where SQL stops being obvious. Most "my query is too complex" problems are really "my query is doing three things at once".

## A worked example

```sql
WITH RECURSIVE category_tree AS (
    -- anchor: the roots
    SELECT id, parent_id, name, 0 AS depth
    FROM categories
    WHERE parent_id IS NULL

    UNION ALL

    -- recursive step: one level deeper
    SELECT c.id, c.parent_id, c.name, t.depth + 1
    FROM categories AS c
    JOIN category_tree AS t ON c.parent_id = t.id
)
SELECT name, depth FROM category_tree ORDER BY depth, name;
```

A recursive CTE needs an anchor and a recursive step, joined with `UNION ALL`. The recursion stops when the recursive step returns no rows.

<Callout type="interview" title="Interview corner">
**When is `EXISTS` better than `IN`?**

`EXISTS` stops at the first match, so it can short-circuit; `IN` may need to build the whole set. `EXISTS` is also null-safe: `NOT IN` with a subquery that returns a single NULL returns no rows at all, which is a classic silent bug. `NOT EXISTS` does not have that failure mode.
</Callout>

## Quick recap

- Use CTEs to name the steps of a query.
- Correlated subqueries re-run per row — watch the cost.
- Prefer `NOT EXISTS` to `NOT IN` when nulls are possible.
