## What you will learn

- Use primary keys, foreign keys, unique, check and not-null constraints together
- Explain why constraints belong in the database and not only in the application
- Add a constraint to an existing table without downtime
- Diagnose a constraint violation and read its error

## Why it matters

Application checks are advisory — two services, two code paths, one bad write. A constraint is the one place the rule is guaranteed to hold.

## A worked example

```sql
ALTER TABLE orders
    ADD CONSTRAINT orders_customer_fk
    FOREIGN KEY (customer_id) REFERENCES customers (id)
    ON DELETE RESTRICT;

ALTER TABLE orders
    ADD CONSTRAINT orders_total_nonneg
    CHECK (total_cents >= 0) NOT VALID;   -- enforce for new rows only
```

`NOT VALID` skips the check on existing rows, which is how you add a constraint to a large table without a long lock. Validate later with `VALIDATE CONSTRAINT`.

<Callout type="interview" title="Interview corner">
**Should validation live in the application or the database?**

Both, for different reasons. The database constraint is the guarantee — it holds no matter which client writes. The application check gives a good error message and a friendly form validation. The database is the source of truth for correctness; the application is the source of truth for usability.
</Callout>

## Quick recap

- Constraints protect the data even when the application is wrong.
- Use a surrogate key unless a natural key is genuinely stable.
- Add constraints to big tables with `NOT VALID`, then validate.
