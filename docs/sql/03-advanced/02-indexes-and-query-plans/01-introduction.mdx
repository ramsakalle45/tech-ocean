## Why it matters

A query plan is the database telling you exactly what it decided. Reading one turns "this query is slow" into "this query is doing a sequential scan because the predicate is not sargable".

## A worked example

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 42
  AND placed_at >= DATE '2026-01-01'
  ORDER BY placed_at DESC;

-- A composite index matching the predicate and the sort:
CREATE INDEX orders_customer_placed_idx
    ON orders (customer_id, placed_at DESC);
```

One index can serve the filter and the sort only if the column order matches: equality columns first, then the range or sort column.

<Callout type="interview" title="Interview corner">
**A query has `WHERE DATE(created_at) = '2026-01-01'` and no index is used. Why?**

The column is wrapped in a function, so the index on `created_at` cannot be used to find the value — the database would have to compute the function for every row. The fix is a sargable predicate: `created_at >= '2026-01-01' AND created_at < '2026-01-02'`, which lets the index do a range scan.
</Callout>

## Quick recap

- Read the actual plan with `EXPLAIN ANALYZE`, not the estimated one.
- Composite index: equality columns first, then range and sort.
- Functions on a column make a predicate non-sargable.
