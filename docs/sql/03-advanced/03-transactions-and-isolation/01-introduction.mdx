## Why it matters

Isolation is the contract your application relies on when it reads two rows and expects them to be consistent. Choosing the wrong level is how you get phantom reads that only appear under load.

## A worked example

```sql
BEGIN;

SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- row lock

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

Always take locks in a consistent order — by primary key ascending — across every transaction. That single rule removes most deadlocks.

<Callout type="interview" title="Interview corner">
**What is a phantom read, and which isolation level prevents it?**

A phantom is a row that appears in a later read of the same range, because another transaction inserted a matching row. Standard `REPEATABLE READ` may allow it, since it guarantees the same rows, not the same set of rows. `SERIALISABLE` prevents it by range-locking the scanned rows. PostgreSQL’s `REPEATABLE READ` uses snapshot isolation and does not allow phantoms.
</Callout>

## Quick recap

- ACID is a guarantee about failure, not about speed.
- Higher isolation means fewer anomalies and more contention.
- Lock rows in a consistent order to avoid deadlocks.
