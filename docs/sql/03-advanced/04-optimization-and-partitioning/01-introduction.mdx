## What you will learn

- Find and fix the N+1 query pattern
- Decide when to normalise and when to denormalise
- Choose a partitioning strategy and know when it is worth the complexity
- Read the database’s own statistics before you change the schema

## Why it matters

Schemas that are fine at 10,000 rows can fall over at 100 million. Partitioning, denormalisation and careful indexing are the tools that keep a database serving as it grows.

## A worked example

```sql
-- N+1: one query for the orders, then one per order for its customer.
-- Fix: fetch in one pass.
SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE o.customer_id IN (42, 87, 105);

-- Range partitioning, pruned by the planner:
CREATE TABLE events (
    id        BIGINT,
    created_at TIMESTAMPTZ NOT NULL,
    payload   JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
```

Partitioning helps most when queries filter on the partition key, letting the planner skip whole partitions.

<Callout type="interview" title="Interview corner">
**When is denormalisation the right call?**

When a read is hot and the join is genuinely expensive, and you can accept the cost of keeping the redundant copy consistent. The classic case is a counter that would otherwise require counting a huge table on every read. Denormalise a derived value that is written rarely and read constantly, and make the update path idempotent.
</Callout>

## Quick recap

- N+1 is the most common performance bug in application code.
- Partition to prune, and partition on the column you filter by.
- Keep statistics fresh so the planner keeps choosing well.
