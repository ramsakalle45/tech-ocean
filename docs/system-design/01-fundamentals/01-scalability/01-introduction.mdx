## A worked example

```text
Capacity planning, in the simplest form:

  requests/second  =  peak_users × requests_per_user
  instances needed = ceil(requests/second ÷ instances_per_second)
  cpu needed       = instances × cpu_per_instance

Work one example end to end:

  100,000 daily users, 5% peak-hour, 10 requests each in that hour
    → 100,000 × 0.05 × 10 = 50,000 requests in the peak hour
    → 50,000 / 3600        ≈ 14 requests/second

With a service that handles 50 requests/second per instance,
plus 3× headroom for traffic spikes:
    → 14 × 3 ÷ 50 ≈ 1 instance → run 3, so one can die

Always state the headroom assumption out loud.
```

The interviewer cares that you did the arithmetic and said your assumptions, not that you reached a particular number.

<Callout type="interview" title="Interview corner">
**Your service handles 1,000 requests per second and 99% of them are reads. How do you scale it?**

Start with the read path, because it is 99% of the traffic. Put a cache in front of the database and see how much of that traffic it absorbs — for many read-heavy services it is most of it. Then scale the database with read replicas, and make sure the service tier is stateless so it can scale horizontally behind a load balancer. I would also check whether the requests need to be synchronous at all.
</Callout>

## Quick recap

- Find the bottleneck before buying anything.
- Scale out for stateless work; scale up when the data is the limit.
- Always plan headroom and single-instance failure.
