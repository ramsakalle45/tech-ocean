## What you will learn

- Distinguish latency from throughput and describe a case where improving one hurts the other
- Break an end-to-end latency budget into its parts
- Use percentiles instead of averages when judging performance
- Explain how concurrency, batching and queueing affect both

## Why it matters

Two numbers decide whether a system feels good. Averages hide the users having a bad time, and a latency budget is the practical tool for knowing where to spend effort.

## A worked example

```python
def percentile(samples: list[float], p: float) -> float:
    """p in 0..1. p99 is the number that matters to your users."""
    ordered = sorted(samples)
    index = min(len(ordered) - 1, int(round(p * (len(ordered) - 1))))
    return ordered[index]

# Averages lie: 99 requests at 10ms, 1 at 2,000ms
samples = [10.0] * 99 + [2000.0]
print(f"avg  {sum(samples)/len(samples):.0f}ms")          # ~30ms — looks fine
print(f"p99  {percentile(samples, 0.99):.0f}ms")          # 2000ms — the truth
```

The average is 30ms and the 99th percentile is two seconds. That gap is the whole argument for percentiles.

<Callout type="interview" title="Interview corner">
**Your API has a 200ms p99 but a 5ms average. Where do you look?**

At the tail, and at what the tail has in common. Slow requests usually share a cause: a cold cache, a lock, a cold connection pool, or a slow downstream that only some requests touch. Look at the slow traces, not the fast ones — and check whether the p99 is a small number of very slow requests or a broad band, because those have different causes.
</Callout>

## Quick recap

- Judge performance at p95 and p99, never the average.
- Write the latency budget before you optimise.
- Queueing and batching buy throughput with latency — consciously.
