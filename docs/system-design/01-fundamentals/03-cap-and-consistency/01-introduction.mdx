## What you will learn

- State the CAP theorem accurately, including what it does not say
- Choose a consistency model per operation, not per system
- Explain eventual consistency and the guarantees you can offer around it
- Use idempotency and compensation to make retries safe

## Why it matters

Every distributed system makes a consistency trade-off, usually without saying so. Being able to name the trade-off and the user-visible consequence is what makes a design defensible.

## A worked example

```python
class PaymentService:
    """Idempotent so the client can retry without double-charging."""

    def charge(self, *, account_id: str, amount_cents: int,
               idempotency_key: str) -> Result:
        existing = self.store.get_by_key(idempotency_key)
        if existing is not None:
            return existing            # same answer, no second charge

        result = self.gateway.charge(account_id, amount_cents)
        self.store.put(idempotency_key, result)
        return result

    def refund(self, *, account_id: str, amount_cents: int) -> Result:
        """Compensating action: a refund, not an undo of the charge."""
        return self.gateway.refund(account_id, amount_cents)
```

You cannot un-charge a card. You issue a compensating transaction, and the saga around it must be designed for partial failure.

<Callout type="interview" title="Interview corner">
**CAP says you must choose between consistency and availability during a partition. Which do you choose?**

It depends on the operation, which is why the useful answer is per-operation. For a payment, you would rather refuse the write than let two nodes both accept it. For a product catalogue, you would rather serve a slightly stale price than return an error. The honest framing is: during a partition you get either consistency or availability, and the design question is which failure you can tolerate for each operation.
</Callout>

## Quick recap

- CAP is about partitions, not about choosing in general.
- Choose a consistency model per operation.
- Make writes idempotent and design compensation for partial failure.
