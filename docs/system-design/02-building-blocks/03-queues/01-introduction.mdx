## What you will learn

- Decide what belongs on a queue and what must stay synchronous
- Design for at-least-once delivery and make consumers idempotent
- Handle a poison message without blocking the queue
- Reason about ordering, backpressure and dead-letter queues

## Why it matters

A queue turns a spike into a backlog. That single property is why queues are everywhere — and it is also why you have to think about duplicates, ordering and failure.

## A worked example

```python
def handle(message: Message) -> None:
    """Idempotent, because the queue promises at-least-once."""
    if already_processed(message.id):
        return

    try:
        result = do_the_work(message)
        mark_processed(message.id)
    except PermanentError as exc:
        dead_letter.send(message, reason=str(exc))   # will never succeed
    except TransientError as exc:
        if message.attempts >= 5:
            dead_letter.send(message, reason=str(exc))
        else:
            requeue_after(message, delay=2 ** message.attempts)  # backoff
```

The `already_processed` check is what turns at-least-once into effectively-once. Make the work idempotent and the delivery guarantee stops mattering.

<Callout type="interview" title="Interview corner">
**A consumer keeps failing on one message and the queue is backing up. What do you do?**

Stop the poison message from blocking the rest. Retry it a bounded number of times with backoff, then move it to a dead-letter queue so the main queue drains. Then fix the cause separately. A common mistake is infinite retries, which means one bad message stalls every consumer behind it and the backlog never clears.
</Callout>

## Quick recap

- Queue work that can be slow, retryable, and independent of the response.
- Assume at-least-once and make the consumer idempotent.
- Always have a dead-letter queue and a bounded retry policy.
