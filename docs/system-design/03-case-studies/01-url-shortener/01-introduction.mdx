## A worked example

```python
ALPHABET = "abcdefghijkmnopqrstuvwxyzABCDEFGHJKLMNPQRSTUVWXYZ23456789"

def encode(number: int, *, length: int = 7) -> str:
    """Base-62 over a counter. No collisions, as long as the counter is unique."""
    out = []
    for _ in range(length):
        number, remainder = divmod(number, len(ALPHABET))
        out.append(ALPHABET[remainder])
    return "".join(reversed(out))
```

A counter is collision-free but guessable. Base-62 of a random 48-bit integer is unguessable and has a birthday-bound collision risk, which you handle by retrying on insert.

<Callout type="interview" title="Interview corner">
**How would you design the key generation?**

Two workable options. A database counter with base-62 encoding guarantees uniqueness and is simple, but the keys are sequential and therefore guessable and enumerable. A random 48- or 64-bit key is unguessable, and collisions are astronomically unlikely at that size; you handle a collision by retrying on insert. For a system that needs both, pre-generate a pool of random keys in advance and hand them out — that removes the round trip to the database at write time.
</Callout>

## Quick recap

- Counter for uniqueness, randomness for unguessability.
- The read path is the hot path — cache it aggressively.
- Do the arithmetic out loud: QPS, storage per URL, and years of growth.
