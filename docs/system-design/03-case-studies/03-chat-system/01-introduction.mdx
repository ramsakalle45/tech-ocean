## Why it matters

Chat is where long-polling, WebSockets, fan-out and message ordering all appear at once. It is a good test of whether you can design for a write-heavy, latency-sensitive workload.

## A worked example

```text
Send path:
  client → API → write to message store (append, sequence number)
                → publish to fan-out service
                     → online sessions: push over WebSocket
                     → offline users: write to per-user inbox

Read path:
  client opens chat → fetch recent messages (by sequence number)
                     → then subscribe to live updates

Why the append-only log:
  - a message has one global order (per conversation sequence number)
  - history is cheap to page through
  - delivery is decoupled from storage

Where the write fan-out hurts:
  10,000 members in one group → 10,000 pushes per message.
  Fix: store once, push a lightweight notification, and let
  each member's session pull what it needs.
```

The fan-out problem is the whole design question in chat. Group size determines the architecture.

<Callout type="interview" title="Interview corner">
**How do you deliver a message to a user who is offline?**

Persist the message to the conversation log, and separately record it in that user’s inbox — the delivery metadata — when they are not connected. When they reconnect, they fetch from the inbox and then subscribe to the live stream. The inbox is per user and can be deleted once read, which keeps it small even when the conversation history is long.
</Callout>

## Quick recap

- Append-only message log with a per-conversation sequence number.
- Fan-out is the hard part: write once, notify many.
- Decouple storage from delivery with a per-user inbox.
