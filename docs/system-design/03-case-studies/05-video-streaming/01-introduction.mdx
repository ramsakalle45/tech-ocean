## What you will learn

- Explain how on-demand and live video differ in their delivery requirements
- Describe the transcoding pipeline and why multiple renditions exist
- Use a CDN for video, and reason about the cost of that choice

## Why it matters

Video is the clearest case in system design of a workload where the read path dwarfs everything else, and where the cost model is bytes, not requests.

## A worked example

```text
On-demand pipeline (hours to days):
  upload → probe → transcode to a ladder → package → store → CDN
  1080p, 720p, 480p, 360p — each a separate file

Live pipeline (seconds):
  ingest → transcode in real time → package → CDN → purge old segments
  latency budget: glass-to-glass under ~5s means aggressive
  packaging, small segment length, and edge-side caching

Cost reality:
  1M viewers × 2 Mbps × 2 hours = 1.8 TB of egress
  A transcoding pipeline is cheaper than a network bill,
  so the ladder is the main lever, not the CDN.

Why a ladder: a phone on 3G should get 360p, not a 1080p
  file it cannot finish downloading.
```

Adaptive bitrate is the reason the system works. The ladder is what makes one video serve a stadium and a phone.

<Callout type="interview" title="Interview corner">
**Why store multiple resolutions instead of one and letting the client scale it?**

Because the client cannot scale it, and because the bitrate is the problem. A 1080p file on a weak connection stalls constantly, because the bits arrive too slowly. Each rendition is encoded at its own bitrate, and the player picks based on measured throughput and switches between renditions as conditions change. The cost is transcoding time and storage; the benefit is that playback actually works.
</Callout>

## Quick recap

- On-demand is a batch pipeline; live is a real-time one.
- The bitrate ladder is what makes playback work on slow connections.
- Video cost is dominated by egress — cache hit ratio is the lever.
