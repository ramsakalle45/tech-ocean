## What you will learn

- Design a multi-channel notification pipeline
- Apply fan-out, deduplication and rate limiting to notifications
- Handle per-channel preferences and quiet hours
- Decide whether delivery guarantees belong in the design

## Why it matters

Notifications are a system where "deliver everything" is the wrong goal. Relevance, deduplication and user trust matter more than throughput.

## A worked example

```text
Pipeline:
  event → notification service
            → preferences check (does this user want it, this way?)
            → dedup check (have we told them this already?)
            → priority + scheduling (quiet hours? digest?)
            → per-channel template render
            → provider queue → push / email / SMS provider

Dedup key example:
  key = hash(user_id, notification_type, entity_id, window)
  with a window of a few minutes, a comment storm on one
  post becomes one push, not forty.

Prioritisation:
  security alert  → always, ignore quiet hours
  marketing      → batch into a daily digest
  social         → drop if the user has not opened the app in 7 days
```

The interesting part of a notification system is what it decides *not* to send.

<Callout type="interview" title="Interview corner">
**How do you stop a user getting forty push notifications when their friends comment on one post?**

Deduplicate at the source. Give each notification a key derived from the user, the type and the entity, and collapse notifications with the same key inside a short window — typically a few minutes. Combine them into a single push ("3 new comments"). This is a queueing and rate problem, not a delivery problem, so it belongs upstream of the provider call.
</Callout>

## Quick recap

- The system’s value is in what it does not send.
- Deduplicate on user, type and entity within a time window.
- Check preferences and quiet hours before you spend money on delivery.
