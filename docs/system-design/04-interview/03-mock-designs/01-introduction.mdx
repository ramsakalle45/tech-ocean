## What you will learn

- Run a 45-minute design for an unfamiliar system
- Deep dive on two components without rambling
- Handle an interruption or a change of requirements mid-design
- Review your own design against the framework

## Why it matters

Reading about design is not the same as doing it. These rounds are timed, and the review at the end is where most of the learning happens.

## A worked example

```text
Mock round — "Design a job scheduler" (45 minutes)

  0–5    Requirements
         "How many jobs, how large, how long do they run, and
          who submits them — users directly, or other services?"

  5–10   Scale
         10M jobs/day, average 30s runtime, 100 peak submissions/s
         → ~10M × 30s = 300M job-seconds per day

  10–20  High-level design
         API → scheduler service → priority queue → worker pool
         → status store (result), plus a results topic
         Workers pull, lease the job, run it, write the result.
         Lease has a TTL so a dead worker’s job is retried.

  20–35  Deep dive
         The queue and the lease protocol.
         - FIFO breaks under one slow job → priority + fair dispatch
         - Exactly-once is not achievable → idempotent job keys
         - A worker dies mid-job → lease expiry, then retry
         - Rate limits per tenant → token bucket per tenant

  35–45  Wrap up
         Monitoring: queue depth, job latency, retry rate, stuck leases.
         What I would do with more time: a priority class system,
         and a dead-letter queue with a replay tool.
```

Note what the deep dive contains: the protocol and its failure modes, not a list of technologies. That is the difference between a senior and a junior answer.

<Callout type="interview" title="Interview corner">
**What does a strong deep dive sound like?**

It picks one component and takes it seriously: the data model, the protocol between two services, the failure mode and the recovery. It states a trade-off — "at-least-once delivery, because exactly-once is not achievable across the queue and the database, so the job must be idempotent" — and it names what would break under load. Listing technologies is not a deep dive.
</Callout>

## Quick recap

- Pick two components and take them seriously.
- Name the trade-off, then name the failure mode.
- Finish with what you would improve given more time.
